# Viva & Demo Guide – Car Price Prediction MLOps

## 1. The 30-second pitch
> "I built a used-car price predictor and, more importantly, the full MLOps lifecycle around it: versioned code on GitHub, automated testing and image builds with GitHub Actions, a Docker container, Kubernetes manifests, infrastructure as code with Terraform, experiment tracking with MLflow, and live monitoring with Prometheus and Grafana. The app is served with Streamlit."

## 4. The ML part (examiners always ask)
- **Data:** CarDekho-style schema (name, year, selling_price, km_driven, fuel, seller_type, transmission, owner). **It is synthetic**, generated by `data/generate_data.py`, because the goal is the MLOps pipeline. Be upfront about this. The real Kaggle CSV drops in as `data/car_data.csv` with no code change.
- **Features:** brand (from name), car age (2025 − year), km driven, and one-hot encoded fuel, seller, transmission, owner.
- **Model:** RandomForestRegressor inside a scikit-learn Pipeline (so preprocessing is saved with the model and cannot drift).
- **Target is log-transformed:** prices are right-skewed; predicting log(price) stabilises training, and we convert back with `expm1`.
- **Results:** R² ≈ 0.97, MAE ≈ ₹48,700 on an 80/20 split. High because the data is synthetic with a clean formula, so don't oversell it.
- **Why RandomForest:** handles non-linear effects (depreciation) and mixed features with little tuning.

## 6. MLflow: how to run it (your "proper MLflow")
```bash
source .venv/bin/activate
pip install -r requirements-dev.txt        # includes mlflow
python -m src.experiments                  # trains 5 configs, each logged as a run
mlflow ui --backend-store-uri sqlite:///mlflow.db     # open http://localhost:5000
```
In the UI:
1. **Experiments → car-price-prediction**: a table of 5 runs with their parameters and metrics.
2. Tick runs → **Compare** → scatter/parallel plot of `max_depth`/`n_estimators` vs `r2`.
3. Click a run → **Artifacts**: the saved model, its signature and input example.
4. **Models → car-price-model**: each run created a new version. Explain: "In production, I'd promote the best version to Production and the app would load that version."

Be honest: the Streamlit app and Docker image load the model file produced by `src.train`; MLflow is used for tracking and the registry, and it is not yet the serving path. Say that as a next step.

## 7. Likely viva questions

**General MLOps**
- *What is MLOps?* DevOps practices applied to ML: automate training, testing, deployment and monitoring so models are reproducible and reliable in production.
- *Why not just a notebook?* Notebooks aren't reproducible, testable or deployable; MLOps gives versioning, automation, and monitoring.
- *CI vs CD?* CI = automatically lint/test/build on every change. CD = automatically deliver the built artifact (here: image to GHCR; deployment step is ready in the workflow, enabled with a kubeconfig secret).

**Docker / Kubernetes**
- *Image vs container?* Image = packaged blueprint; container = running instance.
- *Why train the model during `docker build`?* Container starts instantly and the image is self-contained and versioned with the model.
- *Pod vs Deployment vs Service?* Pod = smallest unit (our container); Deployment keeps N pods running and does rolling updates; Service = stable network endpoint / load balancer for the pods.
- *What does the HPA do?* Adds pods (2→5) when CPU > 70%.
- *Liveness vs readiness probe?* Liveness restarts a hung container; readiness removes a not-ready pod from traffic.

**Terraform**
- *Why Terraform instead of kubectl?* Declarative, versioned, repeatable infra; `plan` shows changes before they happen; state file tracks what exists.
- *What is state?* Terraform's record of real resources; don't commit it (it's in `.gitignore`).

**Monitoring**
- *Push vs pull?* Prometheus **pulls** (scrapes) metrics from `/metrics`.
- *Metric types you used?* Counter (predictions, errors), Histogram (latency, predicted price), Gauge (last prediction).
- *Why monitor an ML app?* Latency/errors show system health; the distribution of predicted prices can reveal **data drift**, i.e. inputs changing from what the model was trained on.
- *What is p95 latency?* 95% of requests are faster than this value.

**MLflow**
- *Tracking vs registry?* Tracking records runs (params, metrics, artifacts); registry versions and stages the chosen model.
- *Why log params?* Reproducibility: you can recreate any past result.

**Honest limitations (say these before they ask)**
1. Synthetic data, so R² is optimistic.
2. MLflow is not in the serving path yet.
3. The CD job validates manifests but doesn't auto-deploy without a cluster secret.
4. No automated retraining or drift alert yet.

**Future work:** real Kaggle data, load the model from the MLflow registry, scheduled retraining, Prometheus alert rules for latency/error rate, canary deploys.

## 8. Cheat-sheet commands
```bash
docker compose up --build -d        # start app + Prometheus + Grafana
docker compose ps                   # show running containers
docker compose down                 # stop
pytest -q                           # run tests
python -m src.experiments           # MLflow runs
mlflow ui --backend-store-uri sqlite:///mlflow.db
cd terraform && terraform plan      # preview infra (needs a cluster context)
kubectl apply -f k8s/ && kubectl get pods -n car-price
```
Useful PromQL: `up`, `car_price_predictions_total`, `rate(car_price_predictions_total[1m])`, `histogram_quantile(0.95, sum by (le)(rate(car_price_prediction_latency_seconds_bucket[5m])))`.
